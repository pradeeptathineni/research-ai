# Change Signals

Start from the user-visible outcome and trace its owner through inputs, state and
consumers. Preserve the [required outcomes](../../docs/product.yaml). A smaller
implementation must still handle meaningful failures and retained knowledge.

Keep one owner per rule. Reuse language/platform facilities and sound existing code
before adding a mechanism. Remove unreachable paths when a verified owner already
provides their behavior. Generalize repeated structure or a real permission/data
boundary; avoid registries, taxonomies and adapters for hypothetical consumers. Names
describe responsibilities, not implementation phases. Version identifiers remain when
stored bytes or downstream consumers depend on their historical meaning.

Research unfamiliar consequential choices at original sources. Compare current code,
native facilities, maintained components and removal on fit, privacy, maintenance,
license, cost and recovery. Record material alternatives and revisit triggers in
planning; popularity and publisher benchmarks do not prove a tool's value here.
Keep semantic interpretation in the bounded model protocol. Never add branches for
evaluation questions, expected answers or a one-off vocabulary.

Before a consequential route or research-method change, compare a strong native
workflow under equivalent constraints. Retain partial/failed runs and unknown costs.
Format checks, quote matches and green fixtures do not establish factual support,
research advantage or human usefulness.

Validate the changed boundary first, then run `npm run verify` for broad changes.
Use isolated fixtures; never load private planning evidence into public fixtures.
Cover denied access, malformed inputs, cancellation, source failures and historical
replay where affected. Inspect the built app for interaction changes, including
keyboard use, small screens and static Pages. Review from a fresh perspective and
fix supported findings before delivery. Repeat checks only after changes or new concerns.

Preserve unrelated edits and private state. Inspect status, branch, remotes and the
final staged diff; commit a coherent change. Push only with task authority, without
rewriting shared history, then verify the remote ref and hosted checks. Stable
releases, candidate execution and recurrence remain separate decisions. Report the
result, relevant validation and actual limits in plain language.

Docs should help someone run or change the product: purpose, commands, ownership,
failures and material constraints. Git retains superseded prose. Studies, screenshots,
handoffs and implementation narration belong in planning. Keep test totals, source
hashes and delivery claims out of product requirements.
